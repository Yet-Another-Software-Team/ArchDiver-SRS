\usevar{\srsNickName} utilize pipeline architecture for analysis workflow allowing its function to be change, add, and alter its analysis.
The application lifecycle will be managed by separating the user interface, controller and pipeline control unit.
The user interface will be responsible for receiving user input and displaying results,
while the controller will manage the flow of data between the user interface and the pipeline control unit.
The pipeline control unit will orchestrate the execution of various analysis components, allowing for flexibility and modularity in the system design.

Key Software Architectural Components:

\begin{itemize}
    \item \textbf{UserInterface:} Responsible for receiving user input and displaying results, providing an intuitive interface for users to interact with the application.
    \item \textbf{Controller:} Manages the flow of data between the user interface and the pipeline control unit, ensuring that user inputs are correctly processed and results are displayed appropriately.
    \item \textbf{PipelineControlUnit:} Invokes and manage execution of pipeline nodes, allowing for dynamic configuration of analysis workflows.
    \item \textbf{ContextStorage:} Responsible for safely storing and managing state information and intermediate data (such as the TOML IR and Graph structures) throughout the analysis process, ensuring that relevant data is accessible to the Controller without interrupting the pipeline.
\end{itemize}

\section{Software Design}
\label{section:software-design}

The runtime behavior of \usevar{\srsNickName} is characterized by a decoupled, state-managed pipeline that separates heavy computational workloads from user interactions. To illustrate the non-trivial interactions between our system's components, we outline the sequence of operations for our primary use cases below.

\subsection{Analysis Pipeline Execution}
The core functionality revolves around the automated extraction and analysis of architectural data. Whether initiated via the graphical interface or a headless CLI environment, the \textbf{Controller} delegates orchestration to the \textbf{PipelineControlUnit} (PCU).

The PCU sequentially invokes the \textbf{CodeParser} to generate the TOML Intermediate Representation (IR), the \textbf{GraphConstructor} to build the dependency graph, and the \textbf{SmellAnalyzer} (incorporating the GraphSAGE model) to classify architectural smells. Crucially, intermediate states are continuously offloaded to the \textbf{ContextStorage}. This design allows the pipeline components to operate as stateless workers and ensures that the UI or CLI can asynchronously fetch the final results without blocking the main execution thread.

\subsection{Interactive Visualization and XAI Explanation}
For the interactive visualization, the system must seamlessly bridge the visual graph data with deep learning explainability. When a user selects a specific architectural smell from the UI, the \textbf{Controller} requests an explanation.

Instead of pre-computing expensive explanations for every node, the PCU retrieves the contextual sub-graph from \textbf{ContextStorage} and invokes the \textbf{GNNExplainer} to extract feature importance and subgraph weights on-demand. These weights, along with raw static metrics, are then passed to the \textbf{SmellExplainer}, which constructs a prompt for the Large Language Model (LLM) to generate a human-readable justification. This lazy-evaluation design ensures that heavy LLM inferences are only executed when explicitly requested, optimizing system resource utilization.

\subsection{Headless Execution and CI/CD Integration}
To support automated workflows such as Continuous Integration (CI), \usevar{\srsNickName} provides a Command-Line Interface (CLI). When initiated via the CLI, the \textbf{Controller} triggers a headless analysis pipeline.

The \textbf{PipelineControlUnit} orchestrates the parsing, graph construction, and smell detection phases exactly as it does in the interactive mode, storing all intermediate and final data within the \textbf{ContextStorage}. However, instead of rendering a graphical dashboard, the Controller fetches the final metrics and detected architectural smells from storage and exports them directly to a structured file format (e.g., JSON or CSV) via the \textbf{FileSystem}. This decoupled design allows the tool to run efficiently in background environments, enabling automated quality gates that can fail a build if critical architectural smells are detected, entirely without the overhead of a graphical user interface.
