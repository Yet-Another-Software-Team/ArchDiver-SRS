\usevar{\srsNickName} utilizes a pipeline architecture for the analysis workflow. The application lifecycle is organized by separating the user interface, the controller, and the pipeline control unit.
The user interface is responsible for receiving user input and displaying results,
the controller coordinates data flow between the UI and the pipeline control unit,
and the pipeline control unit orchestrates execution of analysis components to provide modularity and configurability in the system design.

Key Software Architectural Components:

\begin{itemize}
    \item \textbf{UserInterface:} Responsible for receiving user input and displaying results, providing an interface for users to operate the application. This includes graphical visualization via desktop application, headless execution via CLI, and MCP server.
    \item \textbf{Controller:} Coordinates data flow between the user interface and the pipeline control unit, ensuring inputs are processed and results are exposed.
    \item \textbf{PipelineControlUnit:} Invokes and manages execution of pipeline nodes, supporting configurable analysis workflows.
    \item \textbf{ContextStorage:} Stores and manages state and intermediate data (such as the TOML IR and graph structures) so that relevant data is available to the controller and pipeline components.
\end{itemize}

\section{Software Design}
\label{section:software-design}

The runtime behavior of \usevar{\srsNickName} is characterized by a decoupled, state-managed pipeline that separates heavy computational workloads from user interactions. To illustrate the non-trivial interactions between our system's components, we outline the sequence of operations for our primary use cases below.

\subsection{Analysis Pipeline Execution}
The core functionality revolves around the automated extraction and analysis of architectural data. Whether initiated via the graphical interface or a headless CLI environment, the \textbf{Controller} delegates orchestration to the \textbf{PipelineControlUnit} (PCU).

The PCU sequentially invokes the \textbf{CodeParser} to generate the TOML Intermediate Representation (IR), the \textbf{GraphConstructor} to build the dependency graph, and the \textbf{SmellAnalyzer} (incorporating the GraphSAGE model) to classify architectural smells. Crucially, intermediate states are continuously offloaded to the \textbf{ContextStorage}. This design allows the pipeline components to operate as stateless workers and ensures that the UI or CLI can asynchronously fetch the final results without blocking the main execution thread.

\subsection{Interactive Visualization and XAI Explanation}
For the interactive visualization, the system links the visual graph data with explainability outputs. When a user selects a specific architectural smell from the GUI, the \textbf{Controller} requests a textual explanation.

Instead of pre-computing explanations for every node, the PCU retrieves the contextual sub-graph from \textbf{ContextStorage} and invokes the \textbf{GNNExplainer} to extract feature importance and subgraph weights on demand. These weights, together with raw static metrics, are passed to the \textbf{SmellExplainer}, which constructs a prompt for an LLM to generate a textual justification. The lazy-evaluation approach ensures costly LLM inferences are executed only on demand, reducing resource usage.

\subsection{Headless Execution and CI/CD Integration}
To support automated workflows such as Continuous Integration (CI), \usevar{\srsNickName} provides a Command-Line Interface (CLI). When initiated via the CLI, the \textbf{Controller} triggers a headless analysis pipeline.

The \textbf{PipelineControlUnit} orchestrates the parsing, graph construction, and smell detection phases exactly as it does in the interactive mode, storing all intermediate and final data within the \textbf{ContextStorage}. However, instead of rendering a graphical dashboard, the Controller fetches the final metrics and detected architectural smells from storage and exports them directly to a structured file format (e.g., JSON or CSV) via the \textbf{FileSystem}. This decoupled design allows the tool to run efficiently in background environments, enabling automated quality gates that can fail a build if critical architectural smells are detected, entirely without the overhead of a graphical user interface.

\section{AI and Data Design}
\label{section:ai-data-design}

\subsection{Data Sources and Collection}
We utilize the Q-Scored dataset as our main data source for code repositories with code smells.
The dataset consists of around 50,000 C# and Java projects with code smell annotations.
Our main focus for data preparation will be the reassembling of the database source files
which are hosted on zenodo at: https://zenodo.org/records/4468361 .
Due to the missing documentation of the dataset itself, we will do EDA to understand the
distribution and meaning of each attribute of the dataset.
\\

We will deal with the data class imbalance by querying and sampling 100 projects for each architectural smell.
Since our project utilizes the TreeSitter library for parsing the source code, we map the smell annotations
with the parsed code.
\\

\subsection{Model Design}
\textbf{Model selection}
\\

For the classification model, we use a GraphSAGE model for architectural smell classification.
From existing literature, it has been shown that inductive models outperform transductive models
in code classification tasks {insert ref here}. While GATs can be modelled as an inductive algorithm,
they are prone to overfitting on graph attributes causing poor performance on unseen data. Additionally,
when comparing GraphSAGE to GCN and GAT models, GraphSAGE is significantly faster on graphs with large edges and
nodes. It is up to 7 and 44 times faster than GAT and GCN respectively {insert ref here}.
\\

\textbf{Training methodology}
\\

We use a supervised learning technique for GNN Deep learning on architectural smell classification.
The problem is modeled as a node classification class and we apply GraphSAGE on the input graph.
The input graph contains annotated classes for each node, with each edge having attributes based on the parsed
attributes in the intermediate representation.
\\


\subsection{Evaluation}
For the GraphSAGE evaluation, we use the following metrics
for each architectural smell:
\\
\begin{itemize}
    \item \textbf{Accuracy:} Percentage of correctly identified smells
    \item \textbf{F1:} Harmonic mean of Precision and recall
    \item \textbf{Precision:} Ratio of True positives to the sum of True positives and False positives
    \item \textbf{Recall:} Ratio of True positives to the sum of True positives and False negatives
    \item \textbf{AUC - ROC:} Area Under the Receiver Operating Characteristic curve, representing the model's ability to discriminate between code smell classes across all classification thresholds.
\end{itemize}


For evaluating LLM explanation quality, we aim to conduct a survey with
30 participants to evaluate model explanation quality. Each survey question
is scaled from 1 - 5, with 5 being most satisfactory and 1 being least satisfactory.
The survey contains the following questions:
\\

\begin{enumerate}
  \item Is the explanation relevant to the architectural smell
  \item How accurate is the model's explanation for the smell
  \item Compared to one-shot prompting, is the model's explanation quality better.
  \item How satisfied are you with the model's explanation.
\end{enumerate}
